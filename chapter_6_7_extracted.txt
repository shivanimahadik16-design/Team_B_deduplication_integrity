Chapter 6: System Integration
The four engines were built separately and met only at the contracts in the blueprint, so integration was the first time real requests crossed team boundaries. We followed the order in the integration plan: identity and metadata first, then storage, backup job, dedup and integrity, restore. Rule one was no mock success: a backup counts as done only when real bytes are stored and the checksums match.

Chapter 7: System Validation and Hardening
7.1 Test Strategy and Environment
We tested at five levels. Unit tests with pytest cover each engine's algorithms. Contract tests check each service's requests and responses against the shared envelopes and headers, using mocks written before the producer was ready. Pairwise and end-to-end tests run real requests across engines. Negative and security tests cover bad input, missing credentials and unsafe retries. Performance tests measure latency, load and recovery. Every KPI has a method, a threshold and a place for raw results.
Environment. Services run on team laptops on the college network, with Python 3.14, FastAPI and uvicorn. Shared storage is a Backblaze B2 bucket (S3-compatible, region us-east-005). The load model follows the blueprint: 200 requests per second against Team B, and 200 concurrent users for 30 minutes against the whole system. Reference machine: [CPU, RAM, OS]. [Load tool name and version]. A laptop on Wi-Fi is a same-network demo, not a public deployment, and we describe it that way.
